저는 맛집을 찾거나 물건을 사기 전 후기를 찾을 때 관련 커뮤니티를 검색합니다. 커뮤니티에는 그 분야에 관심이 많은 사람들이 모여 있고 정보 글도 많습니다. 이들이 쓴 글에는 마니아들 사이에서 검증된 정보가 담겨 있어서 광고가 섞이기 쉬운 리뷰나 블로그 글보다 믿을 수 있습니다.

구글도 이 점을 알고 커뮤니티 글이 검색 결과 위쪽에 더 잘 보이도록 알고리즘을 바꾸기도 했습니다. 저는 여기서 한발 더 나아가 오직 커뮤니티 글만을 검색하는 검색 엔진을 직접 만들어 보았습니다. 이 글에서는 커뮤니티 글을 수집하는 스크래퍼부터 역인덱스와 압축, BM25 순위 매기기, 검색 화면까지 모든 과정을 단계별로 설명합니다. 작성한 코드는 모두 제 [GitHub](https://github.com/xkvak/micro-search)에서 확인하실 수 있습니다.

## Scraper

검색 엔진을 구축하기 위한 첫 번째 단계는 검색할 데이터를 확보하는 것입니다. 목표에 따라 Google처럼 기존 데이터를 크롤링할 수도 있고 쿠팡 같은 이커머스나 마켓플레이스처럼 자체 데이터를 사용할 수 있습니다.

제 목표는 "커뮤니티 위주의 검색 엔진"을 만드는 것이므로 한국에서 사용자가 다양한 4개 커뮤니티에서 게시물을 크롤링했습니다. 제 코드는 www을 대상으로 돌아다니는 범용 크롤러가 아니라 정해진 사이트에서 게시물만 골라 저장하는 스크래퍼입니다.

처음부터 웹 전체를 수집하는 크롤러를 만들면 되지 않느냐고 생각할 수도 있습니다. 하지만 우리에게 필요한 것은 커뮤니티의 글이고 커뮤니티의 글은 사이트마다 같은 템플릿을 써서 제목과 본문이 늘 같은 위치에 있습니다. 범용 크롤러를 만들 때 가장 어려운 문제인 "어떤 페이지에서든 본문을 찾아내는 일"을 고민할 필요가 없는 것입니다. 그래서 쓰지 않을 범용성을 위해 일을 키우지 않고 사이트별 구조에 맞춘 스크래퍼를 만들었습니다.

스크래퍼를 만들 때는 새 사이트를 쉽게 추가할 수 있도록 신경 썼습니다. 목록을 넘기며 글 번호를 모으고 글을 받아 저장하는 흐름은 모든 사이트가 같고 달라지는 것은 주소 형식과 페이지에서 제목·본문·댓글을 찾는 위치뿐입니다. 그래서 공통 흐름은 크롤러 하나에 두고 사이트마다 달라지는 부분만 `Site` 클래스로 추상화했습니다. 새 커뮤니티를 추가할 때는 `Site`를 상속한 파일 하나를 만들어 게시판 목록, 목록과 글의 주소 형식, 페이지에서 정보를 뽑는 규칙만 채우면 됩니다.

asyncio 라이브러리를 사용해 수집 속도를 높였습니다. 한 사이트에 요청을 몰아 보내면 차단 문제가 생기므로 사이트 안에서는 정해진 간격을 지키고 동시에 보내는 요청도 두 개로 제한했습니다. 대신 서로 다른 커뮤니티 네 곳을 동시에 수집합니다. 한 사이트가 다음 요청을 기다리는 동안 다른 사이트의 요청이 진행되므로 사이트를 하나씩 차례로 수집할 때보다 전체 수집 시간이 크게 줄어듭니다.

## 인덱스

검색 엔진은 구조적으로 데이터베이스 시스템과 비슷합니다. 문서는 저장소에 저장되고 인덱스가 유지됩니다. 질의는 인덱스를 처리해 일치 항목을 찾은 뒤 사용자에게 돌려주는 방식으로 처리됩니다. 하지만 차이점도 많습니다.

- 데이터베이스 시스템은 임의로 복잡한 질의를 처리해야 하는 반면, 검색 엔진에 들어오는 질의의 대다수는 단어와 구문의 나열이다.
- 데이터베이스 시스템에서 일치 항목은 지정된 논리 조건을 만족하는 레코드다. 검색 엔진에서 일치 항목은 통계적 휴리스틱에 따라 질의에 적절한 문서이며 질의어를 모두 포함하지 않을 수도 있다.
- 데이터베이스 시스템은 일치하는 레코드를 모두 돌려준다. 검색 엔진은 통계적 유사도로 순위를 매긴 일치 항목을 정해진 수만큼 돌려준다.
- 데이터베이스 시스템은 각 레코드에 고유한 접근 키를 부여하고 그 키로 검색할 수 있게 한다. 반면 웹 컬렉션을 질의하면 유사도가 0이 아닌 문서가 수백만 개에 이를 수 있다.

따라서 검색 엔진에는 관계형 조인 같은 복잡한 연산의 비용은 없지만 빠른 응답을 가로막는 다른 장애물이 있습니다. 검색어 하나가 아주 많은 문서에 나타날 수 있고 각 문서에는 보통 아주 많은 단어가 들어 있다는 점입니다. 검색할 때마다 모든 문서를 처음부터 읽으며 검색어를 찾는다면 문서가 늘어날수록 감당할 수 없게 됩니다.

### 역인덱스(Inverted index)

이 문제를 해결하는 자료구조가 역인덱스(inverted index)입니다. 문서는 원래 '문서 → 그 안의 단어들' 순서로 되어 있는데 이를 뒤집어 '단어 → 그 단어가 들어 있는 문서들'로 정리했기 때문에 '역(inverted)' 인덱스라고 부릅니다. 책 뒤의 찾아보기가 용어마다 그 용어가 나오는 쪽 번호를 알려 주는 것과 같습니다.

예를 들어 문서가 세 개 있다고 해 보겠습니다.

| 문서 번호 | 내용               |
| --------- | ------------------ |
| 1         | 아이폰 배터리 교체 |
| 2         | 배터리 배터리 수명 |
| 3         | 아이폰 가격        |

이를 역인덱스로 만들면 다음과 같습니다. 괄호 안은 (문서 번호, 그 문서에서 단어가 나온 횟수)입니다.

| 단어   | 나온 문서 수 | 나온 곳        |
| ------ | ------------ | -------------- |
| 가격   | 1            | (3, 1)         |
| 교체   | 1            | (1, 1)         |
| 배터리 | 2            | (1, 1), (2, 2) |
| 수명   | 1            | (2, 1)         |
| 아이폰 | 2            | (1, 1), (3, 1) |

이제 "아이폰 배터리"를 검색하면 '아이폰'과 '배터리' 두 줄만 보면 됩니다. 문서를 하나도 열어 보지 않고도 두 단어가 모두 나온 문서 1이 가장 관련이 깊고 문서 2와 3은 한 단어씩만 포함한다는 것을 알 수 있습니다. 검색어를 하나도 포함하지 않은 문서는 아예 살펴볼 필요가 없습니다.

### 기본 역파일(Baseline Inverted File)

기본 역파일은 크게 두 가지 구성요소로 이루어집니다. 첫 번째는 단어집(vocabulary)으로 서로 다른 각 단어 _t_ 에 대해 다음을 저장합니다.

- _t_ 를 포함하는 문서의 수 _f<sub>t</sub>_
- 해당 역리스트의 시작 위치를 가리키는 포인터

두 번째 구성요소는 역리스트들의 집합(inverted list)이며 각 리스트는 대응하는 단어 _t_ 에 대해 다음을 저장한다.

- _t_ 를 포함하는 문서들의 식별자 _d_ (순서대로 매긴 문서 번호로 표현)
- 문서 _d_ 안에서 단어 _t_ 가 나타난 빈도 _f<sub>d,t</sub>_ 의 집합

이 밖에도 완전한 검색 시스템을 위해서는 문서 번호를 실제 문서 위치(파일 이름 등)로 바꿔 주는 배열도 필요합니다. 저는 문서 번호마다 파일 경로와 문서 길이(토큰 수)를 담은 docs 배열을 추가로 두었습니다. 검색 엔진을 시작할 때 이 배열을 메모리에 올려 BM25의 문서 길이 보정과 검색 결과 표시에 씁니다.

```python
class SearchEngine:
    def __init__(self, path: Path, k1=1.5, b=0.75) -> None:
        docs = self.db.execute("SELECT path, len FROM docs ORDER BY id").fetchall()
        self.paths = [p for p, _ in docs]
        self.doc_len = array("I", [0, *(n for _, n in docs)])
        self.num_docs = len(docs)
        self.avg_doc_len = sum(self.doc_len) / max(self.num_docs, 1)
```

### 단어집

단어집은 문서에 등장하는 모든 단어와 역리스트 위치가 담겨 있습니다. 제 색인의 단어집에는 단어가 550,000개 있습니다. 이를 dict로 메모리에 적재하면 100MB가 넘게 필요합니다. 게다가 단어가 늘수록 메모리도 그만큼 늘어납니다.

좀 더 효율적인 저장을 위해 B-Tree를 사용합니다. B-Tree는 내부 노드만 메모리에 두고 잎 노드는 디스크에 둬서 메모리를 크게 아낄 수 있습니다. 오직 124KB만 메모리에 적재되고, 나머지는 디스크에 저장됩니다.

단어집에 저장하는 속성은 '단어, 단어가 나온 문서 수, 역리스트의 시작 위치, 역리스트의 바이트 길이' 네 가지이고 테이블 구조는 다음과 같습니다.

```sql
vocab(term TEXT PRIMARY KEY, df INTEGER, off INTEGER, len INTEGER) WITHOUT ROWID
```

### 역리스트 집합

역리스트들의 집합은 postings.bin이라는 바이너리 파일 하나에 저장합니다. 모든 단어의 역리스트를 단어 사전순으로 빈틈없이 이어 붙이고 각 역리스트에는 (문서 번호 d, 등장 횟수 f) 쌍을 문서 번호 오름차순으로 저장합니다.

핵심은 각 역리스트가 연속으로(contiguously) 저장된다는 점입니다. 연속성의 이점은 두 가지가 있습니다. 첫째, 리스트를 한 번의 연산으로 읽거나 쓸 수 있습니다. 둘째, 다음 블록을 가리키는 포인터를 위한 공간이 필요 없습니다.

### 인덱스 생성 과정

이제 인덱스가 저장되는 과정에 대해 설명드리겠습니다. 전체 글을 한 번에 메모리에서 색인하면 메모리가 부족하므로 글을 일정 개수씩 나눈 런(run) 단위로 색인합니다.

1. 글 5,000개(런 하나)를 메모리에서 색인해 그 글들에 나온 단어별 역리스트를 만든다.
2. 만든 역리스트를 단어 사전순으로 정렬해 런 파일에 쓰고 메모리에서 비운다.
3. 모든 글을 처리할 때까지 1~2 과정을 반복한다.
4. 런 파일들을 단어 순서대로 동시에 읽으며 하나로 병합한다.
5. 병합이 끝나면 런 파일을 지우고 완성된 색인으로 기존 색인을 교체한다.

이 방식에서는 색인 중에도 메모리에 런 하나만 올라가고 병합할 때도 런마다 레코드 하나씩만 읽으므로 글이 많아져도 색인에 필요한 메모리가 늘어나지 않습니다.

```python
def build(paths, out=INDEX, run_docs=RUN_DOCS):
    ...
    runs, n = [], 0
    for chunk in batched(paths, run_docs):
        vocab, last, lens = invert((index_text(p.read_text()) for p in chunk), start=n)
        ...
        n += len(chunk)
        runs.append(tmp / f"run{len(runs)}")
        with runs[-1].open("wb") as f:
            for t in sorted(vocab):

    with (tmp / "postings.bin").open("wb") as f:
        db.executemany("INSERT INTO vocab VALUES (?, ?, ?, ?)", merge_runs(runs, f))
    ...
```

## Efficient index representations

효율적인 인덱싱과 질의 처리의 여러 측면을 떠받치는 핵심 아이디어는 압축(compression)입니다. 적절한 압축 기법을 쓰면 공간 사용량과 쿼리 처리 시간을 동시에 줄일 수 있습니다.

압축을 위한 첫 번째 단계는 문서 식별자를 그대로 저장하는 대신 d-gap(문서 번호 간격)을 저장하는 것입니다. 예를 들어 정렬된 문서 번호 시퀀스

```
 7, 18, 19, 22, 23, 25, 63, ...
```

는 다음과 같은 간격으로 표현할 수 있습니다.

```
 7, 11, 1, 3, 1, 2, 38, ...
```

원래 번호는 간격을 앞에서부터 차례로 더하면 그대로 복원됩니다. 역리스트 안의 문서 번호는 항상 오름차순으로 정렬되어 있으므로 간격은 늘 1 이상의 양수가 됩니다.

이 변환이 저장하는 숫자의 최댓값을 줄여 주지는 않습니다. 대신 평균을 크게 낮춥니다. 특히 자주 나오는 단어일수록 문서 사이 간격이 촘촘해서 대부분 1이나 2 같은 작은 수가 됩니다. 제 색인에서 가장 흔한 단어인 '하'는 전체 43,728개 문서 중 35,646개에 나오는데 이 경우 간격의 평균은 1.3 정도에 불과합니다.

그러나 숫자가 작아졌다고 해서 공간이 저절로 줄지는 않습니다. 모든 수를 4바이트에 담으면 7이든 38이든 똑같이 4바이트를 차지하기 때문입니다. 그래서 두 번째 단계로, 작은 수일수록 적은 바이트를 쓰는 가변 바이트(variable-byte, vbyte) 코드를 적용합니다.

방식은 단순합니다. 수를 7비트씩 잘라 한 바이트에 하나씩 담고 남은 최상위 비트는 "뒤에 바이트가 더 이어진다"는 표시로 씁니다. 읽을 때는 최상위 비트가 0인 바이트를 만날 때까지 이어 붙이면 수 하나가 끝납니다. 그래서 1부터 128까지는 1바이트, 16,512까지는 2바이트면 충분합니다.

```python
def vbyte_encode(self, nums):
    out = bytearray()
    for x in nums:
        x -= 1
        while x >= 128:
            out.append(128 + x % 128)
            x = x // 128 - 1
        out.append(x)

    return bytes(out)
```

색인을 만들 때는 문서마다 (간격, 그 문서에서의 등장 횟수) 쌍을 이 함수로 인코딩해 단어의 역리스트 끝에 붙입니다.

```python
vocab[word][1] += vbyte_encode([doc_id - last.get(word, 0), f_dt])
```

실제 색인에서 단어 abcde의 역리스트를 열어 보면 다음과 같습니다.

|                    | 첫 번째 문서 | 두 번째 문서 | 세 번째 문서 |
| ------------------ | ------------ | ------------ | ------------ |
| 문서 번호          | 32,793       | 38,026       | 41,751       |
| d-gap              | 32,793       | 5,233        | 3,725        |
| 등장 횟수          | 1            | 1            | 1            |
| 바이트 (d-gap)     | `98 ff 00`   | `f0 27`      | `8c 1c`      |
| 바이트 (등장 횟수) | `00`         | `00`         | `00`         |
| 합계               | 4바이트      | 3바이트      | 3바이트      |

첫 문서는 4바이트, 그 뒤의 간격은 3바이트로 총 10바이트가 필요합니다. 같은 내용을 앞에서 본 단순한 표현(문서 번호 4바이트 + 빈도 2바이트)으로 저장하면 18바이트가 필요합니다.

색인 전체로 보면 차이가 더 분명합니다. 제 색인의 역리스트에는 (문서, 빈도) 쌍이 14,401,772개 들어 있습니다.

## Ranker

쿼리에 매칭되는 문서 집합을 확보했다면 이를 정렬할 방법이 필요합니다. 가장 잘 알려진 순위 결정 알고리즘은 BM25로 문서의 내용을 기반으로 문서의 순위를 매깁니다. 저는 표준 BM25를 사용하기로 했습니다. 쿼리 $Q$와 문서 $D$ 사이의 점수는 다음과 같이 계산됩니다.

$$
\sum_{i=1}^{n} \mathrm{IDF}(q_i),\frac{f(q_i, D)\times(k_1 + 1)}{f(q_i, D) + k_1\left(1 - b + b,\frac{|D|}{\mathrm{avgdl}}\right)}
$$

각 기호의 의미는 다음과 같습니다.

- 쿼리 $Q$는 키워드 $q_1, q_2, \dots, q_n$으로 이루어져 있다.
- $\lvert D \rvert$는 문서 $D$의 길이다.
- $\mathrm{avgdl}$은 문서의 평균 길이다.
- $k_1$과 $b$는 자유 매개변수(free parameter)이다.
- $f(q_i, D)$는 키워드 $q_i$가 문서 $D$에 나타나는 횟수다.
- $\mathrm{IDF}(q_i)$는 역문서 빈도(inverse document frequency)이며, 다음과 같이 계산한다.

$$
\mathrm{IDF}(q_i) = \ln\left(1 + \frac{N - n(q_i) + 0.5}{n(q_i) + 0.5}\right)
$$

여기서 $N$은 전체 문서 수이고, $n(q_i)$는 $q_i$를 포함하는 문서 수입니다. IDF를 계산하는 방법은 이것 말고도 있지만, 이 방식은 이론적으로 정당화할 수 있다고 합니다.

필요한 수식은 모두 살펴봤으니, 이제 SearchEngine 클래스에서 아직 구현하지 않은 부분을 작성할 수 있습니다. 먼저 상수 $k_1$과 $b$를 클래스의 매개변수로 추가합니다.

```python
def __init__(self, docs: list[str], k1=1.5, b=0.75) -> None:
    self.vocab: dict[str, list] = {}
    self.docs = docs
    self.num_docs = len(docs)
    self.doc_len = array("H", [0]) * (self.num_docs + 1)
    self.avg_doc_len = 0

    self.k1 = k1
    self.b = b
```

이제 점수 계산기를 구현할 준비가 됐습니다. 이 메서드는 쿼리를 받아서, 그 쿼리를 포함하는 모든 문서 번호와 점수를 반환합니다.

```python
def bm25(self, kw: str) -> dict[int, float]:
    result = {}
    idf_score = self.idf(kw)
    decoded = self.vbyte_decode(self.vocab[kw][1])
    doc_id = 0
    for gap in decoded:
        doc_id += gap
        freq = next(decoded)
        numerator = freq * (self.k1 + 1)
        denominator = freq + self.k1 * (
            1 - self.b + self.b * self.doc_len[doc_id] / self.avg_doc_len
        )
        result[doc_id] = idf_score * numerator / denominator

    return result
```

이 메서드는 쿼리 하나를 받아서, 인덱싱된 모든 문서에 대해 그 쿼리의 BM25 점수를 계산합니다. 이 메서드가 있으면 드디어 검색 기능을 구현할 수 있습니다. search 메서드는 검색 엔진이 쿼리를 검색할 때 사용할 메서드입니다.

```python
def search(self, query: str, r=10) -> list[tuple[int, float]]:
    scores = defaultdict(float)
    for t in next(self.tokenize([query])):
        if t in self.vocab:
            for d, s in self.bm25(t).items():
                scores[d] += s

    return heapq.nlargest(r, scores.items(), key=lambda x: x[1])
```

지금까지 만든 것을 모두 합치면, 문서를 색인하고 검색하는 기능을 가진 검색 엔진 클래스가 완성됐습니다.

```python
import json
from contextlib import asynccontextmanager
from pathlib import Path

from fastapi import FastAPI, Request
from fastapi.staticfiles import StaticFiles
from fastapi.templating import Jinja2Templates

from search_engine import SearchEngine, title_and_body

BASE = Path(__file__).parent
INDEX = BASE.parent / "data/inverted"


@asynccontextmanager
async def lifespan(app: FastAPI):
    if not INDEX.exists():
        raise RuntimeError(
            f"{INDEX} 없음. 먼저 `uv run python search_engine.py --index`로 색인을 만드세요."
        )
    app.state.engine = SearchEngine(INDEX)
    yield


app = FastAPI(lifespan=lifespan)
app.mount("/static", StaticFiles(directory=BASE / "static"), name="static")
templates = Jinja2Templates(directory=BASE / "templates")


@app.get("/")
def index(request: Request):
    engine = request.app.state.engine
    return templates.TemplateResponse(
        request, "index.html", {"num_docs": engine.num_docs}
    )


@app.get("/search")
def search(request: Request, q: str):
    engine = request.app.state.engine
    results = [
        post | {"score": s}
        for d, s in engine.search(q)
        if (post := load_post(engine.paths[d - 1]))
    ]
    return templates.TemplateResponse(
        request, "results.html", {"q": q, "results": results}
    )


def load_post(path: str) -> dict | None:
    try:
        md = (BASE.parent / path).read_text()
    except FileNotFoundError:
        return None
    head = md.split("\n---\n", 1)[0].removeprefix("---\n")
    post = {k: json.loads(v) for k, v in (l.split(": ", 1) for l in head.splitlines())}
    body = title_and_body(md).strip().removeprefix(f"# {post['title']}")
    post["excerpt"] = " ".join(body.split())[:200]
    return post
```
